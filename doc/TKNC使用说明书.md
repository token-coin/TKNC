## 核心架构原则（铁律）

### 三层严格分离

```
┌─────────────────────────────────────────────────────────────────────┐
│                    TKNC 架构三层分离（含API Gateway）                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌──────────────┐    ┌──────────────────┐    ┌──────────────┐      │
│  │   Web服务器   │    │      节点         │    │     矿工      │      │
│  │  (种子服务器)  │◄──►│    (tkncd)       │◄──►│ (tknc-miner) │      │
│  │              │    │                  │    │              │      │
│  │ ·纯黄页展示  │    │ ★OpenAI兼容HTTP API│    │ ·仅本地计算   │      │
│  │ ·模型交易平台 │    │   Gateway(:9313)  │    │ ·PoW挖矿     │      │
│  │ ·用户登录鉴权 │    │ ·UPnP/NAT        │    │ ·LLM推理     │      │

│                      ┌───┘  │  └───┐                                │
│                      │      │      │                                │
│               外部用户  P2P   RPC  种子汇报                          │
│               调用API  (9333) (9331) (Web展示)                       │
│                                                                     │
│  ⚠️ 三种IP地址绝对不能搞混：                                         │
│  · 66.154.101.183 = 种子服务器IP（只做矿工展示，不提供API！）          │
│  · 节点公网IP = 每台运行节点的电脑自己的IP（提供OpenAI兼容API！）    │

```

### 三条核心铁律

> 以下三条铁律覆盖整个 TKNC 计费与网络模型，后续所有章节均以此为准。

```
铁律 1 【零中转】种子服务器 / Web 绝不参与任何数据或信令中转
        · 推理数据 = 客户节点 ──直连P2P──→ 矿工节点，端到端
        · 种子服务器只做：矿工黄页展示、钱包签名登录、价格展示
        · 不做：请求转发、API 路由、信令交换、token 任何处理

铁律 2 【先用后付 + 实时上链】不预付、不锁仓、不留存
        · 推理先发生，按真实产出 token 计费
        · 客户节点本地累记消费，每累计满 1 TKNC → 客户钱包直接发一笔
          链上转账到矿工钱包并上链（from 客户钱包 → to 矿工钱包）
        · Escrow 仅记录消费限额（LevelDB），不锁仓、不托管
        · 服务器崩溃、节点损坏不影响历史已上链的交易

铁律 3 【推理前握手校验】双方 token 计数一致才建立推理链路（✅ 已实现 — HTTP 网关路径）
        · 正式推理前，矿工先做一次微型真实推理产出几个 token
        · 客户节点用同款 tokenizer 重数，与矿工节点自报计数核对
        · 双方一致 → 建立推理链路；不一致 → 立即拒绝连接
        · 防止双方计价口径不同导致的计费作弊
        · 实现位置：`tknc_setinferproxytarget` RPC → 矿工 `/v1/chat/handshake` 端点
        · P2P 路径握手（HANDSHAKE_REQ/RESP）待实现
```

### 模块分工表

| 模块 | 职责 | 禁止 |
|------|------|------|
| **tkncd（节点）** | 客户节点 / 矿工节点**同一程序、按角色区分**：UPnP/NAT-PMP、公网地址获取（IPv4/IPv6/域名）、种子注册、P2P网络(9333)、RPC(9331)、区块链与钱包；**客户节点**：发起握手校验（✅ 已实现 — HTTP 路径）、本地累记消费、每满1TKNC发起链上转账；**矿工节点**：托管本地矿工(127.0.0.1:9332)、向全网广播矿工能力 | 禁止挖矿（挖矿归矿工进程）、禁止加载LLM模型（推理归矿工进程）、**禁止作为推理数据中转**、禁止替任何一方汇报/篡改token数 |
| **tknc-miner（矿工）** | 本地计算：PoW挖矿、LLM模型推理（**默认PoW模式，被调用时切换LLM**）；**通过RPC连接本机矿工节点获取任务和提交结果**；**绑定 127.0.0.1:9332（仅本地！本机节点通过localhost访问）** | **禁止绑定0.0.0.0！禁止P2P/UPnP！公网地址由其矿工节点管理！**；**默认仅使用GPU**（CPU需显式启用） |
| **tknc-cli（命令行）** | RPC指令发送 | 禁止独立运行 |
| **Web服务器（种子节点）** | **纯黄页展示层**：矿工列表展示（矿工节点启动后主动汇报在线状态）、用户登录鉴权（钱包签名）、价格/能力展示、矿工发现辅助 | **禁止POW挖矿、禁止LLM推理、禁止任何形式中转（含请求/数据/信令）、禁止token计费、禁止余额管理、禁止提供推理API、禁止持有钱包私钥** |

> ⚠️ **节点角色说明**：tkncd 是统一的节点程序。**矿工节点** = 本机跑着 tknc-miner 的节点，对外提供算力；**客户节点** = 发起推理请求并付费的节点。推理发生在**客户节点 ↔ 矿工节点**之间，二者通过 P2P 直连。

### 双部署模式

TKNC 支持两种部署模式，矿工可根据自身网络条件选择：

| 模式 | 描述 | 矿工连接 | 对外通信 | 适用场景 |
|------|------|---------|---------|---------|
| **SOLO 模式** | 本地节点 + 本地矿工 | `127.0.0.1:9331` | 矿工仅连本地节点RPC | 有公网IP的服务器/独立机器 |
| **矿池模式** | 远程共享节点 + 本地矿工 | `-rpcconnect=远程IP:9331` | 矿工连远程节点RPC获取任务+提交结果 | 家庭挖矿机、无公网IP |

> **重要说明**：两种模式下矿工都通过 **RPC(9331)** 连接节点获取挖矿任务和提交结果——SOLO 模式连本地节点，矿池模式连远程节点。矿工**绑定 127.0.0.1:9332（仅本地！禁止0.0.0.0！）**，外部用户通过**节点的 OpenAI 兼容 HTTP API Gateway(:9313)** 调用推理服务（不是直连矿工！）。公网地址由节点管理。矿工**不参与P2P网络(9333)**、**不做UPnP端口映射**（节点负责）。两种模式都支持，由用户自行选择。

### 矿工模式切换机制

```
┌─────────────────────────────────────────────────────────┐
│                  矿工作模式自动切换                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  [默认状态] PoW挖矿 ──────────────────────────────── 运行 │
│      │                                                 │
│      │ 收到节点的LLM推理请求                             │
│      ▼                                                 │
│  [切换到] LLM推理 ───────────────────────────────── 执行 │
│      │                                                 │
│      │ 推理完成 → 返回结果+prompt_tokens/completion_tokens给节点               │
│      ▼                                                 │
│  [切回] PoW挖矿 ──────────────────────────────────── 继续 │
│                                                         │
│  切换条件：                                              │
│  · 有LLM推理请求 → 立即切换到LLM模式                     │

│  · 无请求时 → 持续PoW挖矿                               │
│                                                         │

```

## 程序与配置

系统中需要用到三个程序：

- `tkncd.exe` — 节点程序（对外通信网关、区块链、钱包、P2P网络、WebSocket代理、Token统计、公网地址管理）。路径：`D:\TKNC\build_mingw\bin\tkncd.exe`
- `tknc-cli.exe` — 命令行工具（通过 RPC 发送指令给节点）。路径：`D:\TKNC\build_mingw\bin\tknc-cli.exe`
- `tknc-miner.exe` — 矿工程序（本地挖矿+LLM推理，**绑定 127.0.0.1:9332 仅本地！节点通过localhost访问**）。路径：`D:\TKNC\build_mingw\bin\tknc-miner.exe`

> 以下所有操作都在终端（PowerShell）中执行。如果终端提示命令找不到，先进入目录 `D:\TKNC\build_mingw\bin\`。

配置文件位置：`D:\TKNC\build\data\tknc.conf`，内容包含 RPC 用户名 `tkncadmin`、密码（32位随机字符串，查看 `tknc.conf` 获取）、RPC 端口 `9331`、P2P 端口 `9333`。

**节点端口（tkncd.exe 监听）**：

| 端口 | 用途 | 监听地址 | 公网可达 | 说明 |
|------|------|---------|---------|------|
| **9313** | **OpenAI兼容HTTP API Gateway** | **矿工节点: 0.0.0.0 ★** / 种子节点: 127.0.0.1 | **矿工节点: ✅ 是** / 种子节点: ❌ 否 | **★核心！外部用户调用LLM推理的唯一入口（类似 api.openai.com）。矿工节点必须绑定0.0.0.0，否则外部请求无法到达！种子节点不提供推理，绑定127.0.0.1即可。** |
| 9331 | RPC | 127.0.0.1 | ❌ 否 | 本地RPC调用（tknc-cli、Web服务器、矿工连接节点）。**禁止公网暴露！**（见Q7安全加固） |
| 9333 | P2P网络 | 0.0.0.0 | ✅ 是 | 节点间区块同步+推理请求路由。**必须公网可达！** |

> **铁律**：
> - **9313端口是节点的OpenAI兼容API Gateway**，这是外部用户调用推理服务的唯一HTTP接口
> - **⚠️ 矿工节点的9313端口必须绑定0.0.0.0！** 代码默认绑定127.0.0.1，矿工节点需通过 `-gatewaybind=0.0.0.0` 参数或 tknc.conf 中 `gatewaybind=0.0.0.0` 配置来开放公网访问。否则API Key创建后返回的endpoint将无法连接！
> - 节点**不使用9332端口**。9332是矿工的独占端口，仅绑定`127.0.0.1`
> - 外部用户通过 `http://[节点公网IP]:9313/v1/chat/completions` 调用API（不是种子服务器！）
> - 种子服务器(66.154.101.183)只做展示，不提供任何API调用能力

**矿工端口（tknc-miner.exe 监听）**：

| 端口 | 用途 | 监听地址 | 公网可达 | 说明 |
|------|------|---------|---------|------|
| 9332 | 矿工API | **127.0.0.1** | ❌ 否 | **仅本地访问！只有本机节点能通过localhost访问。矿工通过RPC(9331)连节点获取任务。** |

> ⚠️ **铁律**：矿工API端口9332**必须绑定127.0.0.1**，禁止绑定0.0.0.0！所有外部请求由节点的API Gateway(:9313)接收后经localhost转发到矿工。

客户端使用 `tknc-cli.exe` 发送指令，格式为：

```
tknc-cli.exe -rpcport=<端口> -rpcuser=tkncadmin -rpcpassword=<RPC密码> <命令> [参数...]
```

## 一、启动节点

### 1.1 本地开发模式

第一步：打开终端，启动节点程序：

```
D:\TKNC\build_mingw\bin\tkncd.exe -datadir=D:\TKNC\build\data -conf=D:\TKNC\build\data\tknc.conf -daemon=0
```

第二步：等待节点初始化完成。终端会显示 `P2P listening on 0.0.0.0:9333` 和 `RPC listening on 127.0.0.1:9331`（RPC仅本地监听，见Q7安全加固）。

第三步：终端中看到 `init message: Done loading` 后，节点启动完成。保持此终端打开，后续命令在另一个终端中执行。

> 如果区块数据损坏导致启动失败，删除 `D:\TKNC\build\data\mainnet\blocks` 和 `chainstate` 目录后重试。

### 1.2 分布式部署模式（远程服务器/种子节点）

TKNC 支持分布式部署：节点运行在远程服务器（种子节点），矿工在本地连接远程节点。

**种子服务器启动节点**（同时运行Web服务）：

```
tkncd.exe -datadir=/path/to/data -conf=/path/to/tknc.conf -daemon=0
```

**关键配置项**（tknc.conf）：

```ini
[main]
rpcuser=tkncadmin
rpcpassword=<RPC密码>
server=1
printtoconsole=1
rpcport=9331
port=9333
daemon=0
rpcallowip=127.0.0.1
rpcallowip=::1
rpcbind=127.0.0.1
bind=0.0.0.0
bind=[::]:9333
addressindex=1
```

> **安全提示**：RPC 端口 9331 必须绑定 `127.0.0.1`，禁止对公网开放。P2P 端口 9333 需对公网开放。详见 Q7 安全加固记录。
>
> **AddressIndex 说明**：`addressindex=1` 启用原生地址索引，支持 O(k) 时间复杂度的地址 UTXO 查询（k = 地址的 UTXO 数量）。区块浏览器依赖此索引实现地址余额秒级加载。详见 Q8 AddressIndex 说明。
>
> **种子节点职责**：运行节点 + Web服务（nginx反向代理到Express:3000，对外暴露端口80）。**种子节点不参与POW挖矿、不运行矿工、不提供LLM推理、不做请求中转**。

## 二、钱包操作

> 以下命令需要在节点已启动的基础上执行。打开新终端进行操作。

### 2.1 创建钱包

第一步：选择一个钱包名称，例如 `my-wallet`。

第二步：输入创建命令：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> createwallet my-wallet
```

第三步：成功后终端显示钱包名称。如果提示"Database already exists"，说明该名称已被使用，换一个名称即可。

### 2.2 生成收款地址

第一步：确认钱包已加载（使用 `listwallets` 命令检查）。

第二步：输入生成地址命令：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcwallet=my-wallet getnewaddress
```

第三步：终端会显示一个以 `token1` 开头的 42 位地址，例如 `token1qh0hyp32j3jff90lvmmgt0rwxelpuf4tuya6grm`。这个地址用来接收 TKNC。

### 2.3 查询余额

第一步：确认钱包已加载。

第二步：输入查询命令：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcwallet=my-wallet getbalance
```

第三步：终端显示当前余额（单位 TKNC）。

### 2.4 转账

第一步：确认发起方钱包已加载，且有足够余额。

第二步：输入转账命令，指定目标地址和金额：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcwallet=my-wallet sendtoaddress <目标地址> <金额>
```

例如：转账 100 TKNC 到地址 `token1abc...`：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcwallet=my-wallet sendtoaddress token1abc... 100
```

第三步：终端显示交易哈希（TXID），表示交易已提交。挖出一个区块后交易确认。

### 2.5 查看钱包信息

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcwallet=my-wallet getwalletinfo
```

显示钱包名称、密钥池大小、最后区块高度等信息。

### 2.6 列出已加载的钱包

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> listwallets
```

### 2.7 恢复钱包

第一步：确保有备份文件（通常位于 `D:\TKNC\data\backups\`）。

第二步：输入恢复命令：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> restorewallet <钱包名称> <备份文件路径>
```

第三步：恢复完成后，用 `getbalance` 确认余额。

### 2.8 卸载钱包

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> unloadwallet my-wallet
```

## 三、生成区块（获取初始币）

> 在主网模式下，通过挖矿生成区块来获取初始 TKNC。难度自动调节，目标出块时间 120 秒。

第一步：生成 101 个区块使币可用（这是 TKNC 的规则，前 100 个区块的奖励不能立即使用）：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> generatetoaddress 101 <你的钱包地址>
```

第二步：确认余额到账：


第三步：后续如需更多币，可继续生成区块：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> generatetoaddress 1 <你的钱包地址>
```

> **难度说明**：TKNC 采用 KASPA 风格动态难度调节算法(DAA)，目标出块时间 120 秒/块。网络算力变化时难度自动调整。

## 四、启动矿工

> ⚠️ 严格按以下三步操作：启动 → 检查 → 关闭。任何其他任务在关闭矿工之后执行。
>
> ⚠️ **铁律 1**：矿工**通过 RPC 连接节点获取任务**——可以连本地节点(127.0.0.1:9331)，也可以连远程节点(IP:9331)。这是矿工唯一允许的外部连接。
>
> ⚠️ **铁律 2（GPU优先）**：矿工**默认仅使用 GPU** 进行 PoW 挖矿和 LLM 推理。**无可用 GPU 时禁止启动**，除非显式添加 `-use-cpu` 参数强制启用 CPU 模式。
>
> ⚠️ **铁律 3（连接检查）**：矿工启动后**必须先验证与节点的RPC连接**，连接失败则拒绝进入挖矿/推理状态。

### Step 1：启动矿工 — 启动前必读

**节点必须已启动**：无论是本地节点还是远程节点，必须确保 tkncd 已正常运行并同步区块。

#### ⚠️ PowerShell 参数格式重要说明

**在 PowerShell 中启动程序时，IP 地址参数必须用引号包裹！**

```powershell
# ❌ 错误：PowerShell 会将 IP 地址中的点号(.)视为特殊字符，导致截断
-rpcconnect=127.0.0.1  → 实际传递 "127" (length=3) → RPC 连接失败

# ✅ 正确：使用引号确保完整 IP 地址传递
"-rpcconnect=127.0.0.1"  → 传递 "127.0.0.1" (length=9) → RPC 连接成功
```

此规则适用于所有包含点号的参数：`-rpcconnect`、`-public-ip` 等。（注意：**不再需要 `-model` 参数**，模型路径由节点通过RPC下发）

#### 完整启动参数表

| 参数 | 必需 | 默认值 | 说明 |
|------|------|--------|------|
| `-wallet=<地址>` | ✅ | 无 | 矿工钱包地址，挖矿奖励和推理费用接收地址 |
| `-rpcconnect=<IP>` | ❌ | `127.0.0.1` | 节点IP地址——本地模式省略（用默认值），**矿池模式必须指定**为远程节点IP |
| `-rpcport=<端口>` | ❌ | `9331` | 节点RPC端口，默认9331 |
| `-rpcuser=<用户>` | ❌ | `tkncadmin` | 节点RPC用户名 |
| `-rpcpassword=<密码>` | ❌ | `<RPC密码>` | 节点RPC密码 |
| `-no-inference` | ❌ | 不启用 | **仅挖矿模式**：不提供LLM推理服务，只做PoW挖矿 |
| `-use-cpu` | ❌ | **不启用** | **强制CPU模式**：默认仅用GPU，无GPU时拒绝启动；**必须加此参数才允许CPU挖矿/推理** |
| `-n_ctx=<N>` | ❌ | `131072`（128K） | **LLM上下文窗口大小**（token数）。真实限制是GPU VRAM。支持1M上下文模型（如GLM5.2）：`-n_ctx=1048576`。腾讯级数据中心可设置更大值 |

#### 启动命令（两种模式）

```powershell
# ──────────────────────────────────────────────
# 模式 A：SOLO 本地模式 — 连接本地节点
# 零参数（仅需 -wallet），RPC 默认连 127.0.0.1:9331
# ──────────────────────────────────────────────
D:\TKNC\build_mingw\bin\tknc-miner.exe -wallet=你的钱包地址

# ──────────────────────────────────────────────
# 模式 B：矿池模式 — 连接远程节点
# 必须指定 -rpcconnect 指向远程节点IP
# ──────────────────────────────────────────────
D:\TKNC\build_mingw\bin\tknc-miner.exe `
    -wallet=你的钱包地址 `
    "-rpcconnect=<远程节点IP>" -rpcport=9331 `
    -rpcuser=tkncadmin -rpcpassword=<RPC密码>

# ──────────────────────────────────────────────
# 模式 C：仅挖矿（不提供LLM推理）+ 连远程节点
# ──────────────────────────────────────────────
D:\TKNC\build_mingw\bin\tknc-miner.exe `
    -wallet=你的钱包地址 `
    "-rpcconnect=<远程节点IP>" -rpcport=9331 `
    -rpcuser=tkncadmin -rpcpassword=<RPC密码> `
    -no-inference

# ──────────────────────────────────────────────
# 模式 D：强制 CPU 模式（不推荐，仅用于无GPU环境）
# 必须显式添加 -use-cpu 参数，否则无GPU时拒绝启动
# ──────────────────────────────────────────────
D:\TKNC\build_mingw\bin\tknc-miner.exe `
    -wallet=你的钱包地址 `
    -use-cpu
```

**矿池模式示例**（连接到 IP 为 203.0.113.50 的远程节点）：

```powershell
tknc-miner.exe -wallet=token1q... "-rpcconnect=203.0.113.50" -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码>
```

#### 矿工启动自检流程（严格按顺序执行）

启动后，矿工内部依次执行以下检查，**全部通过后才进入工作状态**：

```
1. 硬件检测阶段
   ├─ 检测可用 GPU（CUDA/Vulkan/OpenCL）
   │  ├─ ✅ 检测到 GPU → 使用 GPU 进行 PoW + LLM 推理
   │  └─ ❌ 无可用 GPU → 检查是否有 -use-cpu 参数
   │        ├─ ✅ 有 -use-cpu → 切换到 CPU 模式（性能警告）
   │        └─ ❌ 无 -use-cpu → 报错退出："No GPU available. Add -use-cpu to force CPU mode."
   │
2. 节点连接检查阶段（连接检查机制）
   ├─ 通过 RPC 连接目标节点（本地 127.0.0.1:9331 或 远程IP:9331）
   ├─ 验证 RPC 认证（user/password）
   ├─ 检查区块链同步状态（区块高度 > 0）
   ├─ ✅ 连接成功且链已同步 → 继续
   └─ ❌ 连接失败 / 未同步 → 报错退出："Failed to connect to node at <IP>:<port>"
   │
3. 模型加载阶段（除非加了 -no-inference）
   ├─ 通过 RPC 从节点获取模型路径和元数据
   ├─ 加载模型到 GPU 显存（或 CPU 内存）
   ├─ ✅ 模型加载成功 → 继续
   └─ ❌ 模型加载失败 → 如加了 -no-inference 则跳过（仅挖矿），否则报错退出
   │
4. 启动完成
   ├─ 矿工 API 端口监听 127.0.0.1:9332
   └─ 进入 PoW 挖矿模式（默认），等待 LLM 推理请求时自动切换
```

**正常启动终端输出顺序**：

1. `[GPU] Detected: NVIDIA GeForce RTX ...` 或 `[CPU] Mode enabled (forced by -use-cpu)` — 硬件检测结果
2. `[Node] Connecting to 127.0.0.1:9331 ...` → `[Node] Connected. Block height: N` — 节点连接
3. `[LLM] Model loaded: qwen2 1B Q4_K - Medium` — 模型加载成功（**路径由节点RPC下发**）
4. `[LLM] GPU: ... Memory: X GB used` — GPU 加载信息
5. `API listening on **127.0.0.1**:9332` — 矿工 API 端口（**仅本地监听！**）
6. `Mining started` — **进入 PoW 挖矿模式**
7. `Mode: POW` — 当前模式显示

> **说明**：
> - 模型路径由节点通过RPC自动下发给矿工，**不需要 `-model` 参数**
> - 矿工监听 `127.0.0.1:9332`（仅本地访问，节点通过localhost转发外部请求）
> - **GPU优先**：默认仅用GPU，无GPU时拒绝启动，CPU需显式 `-use-cpu` 启用

### Step 2：检查矿工状态（从启动日志到端口验证）

第一步（启动日志检查）：确认矿工终端输出包含以下关键行：

| 检查项 | 应出现的日志 | 说明 |
|--------|--------------|------|
| ✅ GPU 检测 | `[GPU] Detected: ...` 或 `[CPU] Mode enabled` | 确认硬件加速已启用 |
| ✅ 节点连接 | `[Node] Connected. Block height: N` | 确认已连上节点且链已同步 |
| ✅ 模型加载 | `[LLM] Model loaded: ...` | 确认模型加载成功（加了 `-no-inference` 则无此行） |
| ✅ 端口监听 | `API listening on 127.0.0.1:9332` | 确认仅本地监听（节点通过localhost转发外部请求） |
| ✅ 挖矿启动 | `Mining started` + `Mode: POW` | 确认进入 PoW 模式 |

第二步（端口检查）：确认端口 9332 处于**本地**监听状态。终端输入 `netstat -ano | findstr "127.0.0.1.*9332.*LISTENING"`，有输出表示正常。

✅ **重要验证 1**：必须看到 `127.0.0.1:9332` 而非 `0.0.0.0:9332`，说明矿工正确绑定本地地址，仅允许节点通过localhost访问！

⚠️ **重要验证 2**：如果启动日志中没有 `[Node] Connected`，说明矿工无法连接到节点——检查节点是否已启动、`-rpcconnect` 参数是否正确、防火墙是否放行9331端口。

⚠️ **重要验证 3**：如果启动日志中显示 `No GPU available` 且未加 `-use-cpu`，说明无GPU且未强制CPU模式——要么安装GPU驱动，要么加 `-use-cpu` 参数。

第三步（API 检查）：发送推理请求测试（通过localhost，仅在未加 `-no-inference` 时需要）：

```
Invoke-RestMethod -Uri "http://127.0.0.1:9332/api/v1/chat" -Method Post -Body '{"api_key":"","messages":[{"role":"user","content":"What is 1+1? Answer in one sentence."}]}' -ContentType "application/json" -Headers @{"Content-Type"="application/json"}
```

如果返回推理结果（如 `1+1 equals 2.`），说明矿工正常工作。

### Step 3：关闭矿工

第一步：在矿工终端中按 `Ctrl+C`，或执行：

```
taskkill /F /IM tknc-miner.exe
```

第二步：确认端口 9332 已释放。终端输入 `netstat -ano | findstr "9332.*LISTENING"`，应无输出。

## 五、LLM 推理服务（节点公网地址 + 握手校验 + 先用后付）

> 本节描述基于**节点公网地址**的架构。矿工本身不获取公网IP、不对外通信、不注册到Web。公网交互与对外的 P2P 推理连接由**节点**完成。计费采用**先用后付 + 每1TKNC实时上链**，详见 §5.3 步骤4。

### 5.1 架构总览 — 四层分工

> **核心原则**：TKNC 是**先用后付 + 握手对账的去中心化算力市场**。推理数据端到端直连，资金按消费实时上链，不预付、不锁仓、不中转。

```
┌─────────────────────────────────────────────────────────────────┐
│              TKNC 推理服务架构（四层分工）                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Layer 1: 区块链（最终真相层）                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  链上交易 = 客户钱包 → 矿工钱包 的普通转账                 │   │
│  │  · 客户节点每累计消费满 1 TKNC，发起一笔直接转账并上链    │   │
│  │  · 资金从不曾停留在任何托管合约中                          │   │
│  │  · Escrow 仅记录消费限额（LevelDB），不锁仓 → 服务器崩坏不影响已上链交易 │   │
│  └─────────────────────────────────────────────────────────┘   │
│         ↓                                                       │
│  Layer 2: 节点（P2P 端到端 + 双方对账权威）                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  客户节点 (tkncd) 与 矿工节点 (tkncd) 通过 P2P 直连      │   │
│  │  客户节点职责：                                           │   │
│  │  · 本地用同款tokenizer计数token（握手校验已实现）         │   │
│  │  · 本地累记消费金额                                       │   │
│  │  · 每满1 TKNC 用客户钱包私钥发链上转账给矿工              │   │
│  │  矿工节点职责：                                           │   │
│  │  · 托管本地矿工(127.0.0.1:9332)、向全网广播矿工能力       │   │
│  │  · 流式返回推理token（配合握手校验已实现）                 │   │
│  └─────────────────────────────────────────────────────────┘   │
│         ↓                                                       │
│  Layer 3: 矿工（执行层，仅本地）                                    │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  Miner (tknc-miner)                                      │   │
│  │  · 本地计算：PoW 挖矿 + LLM 推理                         │   │
│  │  · 通过 RPC 连接本机矿工节点获取任务/提交结果             │   │
│  │    （本地 127.0.0.1:9331，矿池模式可连远程矿工节点）       │   │
│  │  · **GPU优先**：默认仅用GPU，无GPU需加 -use-cpu 启用CPU  │   │
│  │  · **绑定 127.0.0.1:9332（仅本地！本机节点通过localhost访问）**    │   │
│  │  · 推理完成后向本机节点报告结果+tokens                    │   │
│  └─────────────────────────────────────────────────────────┘   │
│         ↓                                                       │
│  Layer 4: Web（纯黄页展示层 — 不中转/不碰数据/不持有资金）         │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  Web (Express) — 黄页展示                                  │   │
│  │  · 用户登录鉴权（钱包签名）                              │   │
│  │  · 矿工列表展示（从 P2P 网络接收节点广播）                │   │
│  │  · 价格 / 模型 / 能力展示                                │   │
│  │  · ❌ 禁止：任何中转(含信令)、token计费、余额管理、       │   │
│  │           持有钱包私钥、提供推理API                       │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  数据流（客户节点 ──直连──→ 矿工节点，Web 仅做黄页）：             │
│                                                                 │
│  阶段1: 发现矿工（只读黄页，经过 Web）                            │
│  客户浏览器 ──HTTP(80)──→ Web(Express)                          │
│       │  1.钱包签名登录     │  2.返回可用矿工列表(含公网地址+价格)│
│       ※ Web 不参与后续任何推理交互                                │
│                                                                 │
│  阶段2: 握手校验 + 正式推理（客户节点 ↔ 矿工节点 直连）            │
│  客户节点 ──P2P(9333)──→ 矿工节点                                │
│       │                  │                                     │
│       │  3.握手校验(微型真实推理产出几个token→客户重数核对)        │
│       │     一致→建立推理链路  不一致→拒绝连接                   │
│       │  4.POST APIREQ(推理请求)                                 │
│       │                  │  5.转发本地矿工(127.0.0.1:9332)推理    │
│       │                  │  6.逐token流式返回 + 矿工计token数     │
│       │  7.客户节点实时累加自己计数                              │
│       ←── APIRESP { content, 双方token计数 } ─────────────────┘│
│                                                                 │
│  阶段3: 计费上链（每满1 TKNC，客户节点主动发起）                   │
│  客户节点本地累记消费 → 累计满1TKNC整数倍？                       │
│       ├─ 是 → 客户钱包→矿工钱包 链上转账，广播确认               │
│       └─ 否 → 继续累记                                          │
│                                                                 │
│  · 链上只存模型元数据（名称/哈希/大小/价格/发布者）              │
│  · 实际 GGUF 模型文件由矿工本地持有，用户无需下载                │
│  · 矿工绑定 127.0.0.1:9332（仅本地！推理数据由 P2P 直连承载）   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 节点公网地址设置（由节点完成，不是矿工！）

> ⚠️ **铁律**：公网地址的获取、设置、上报全部由**节点（tkncd）**执行。**矿工（tknc-miner）不参与任何公网相关操作！**

#### 公网地址检测与上报流程（矿工启动时自动执行）

```
┌─────────────────────────────────────────────────────────┐
│  矿工启动 → 硬件检测 → 节点连接 → 公网地址自检 → 自动上报  │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  矿工启动流程（严格按顺序）：                             │
│  1. 矿工(tknc-miner) 启动                                │
│  2. 硬件检测（GPU优先）：                                │
│     ├─ 检测可用 GPU（CUDA/Vulkan/OpenCL）                │
│     ├─ ✅ 有GPU → 使用GPU进行 PoW + LLM 推理             │
│     └─ ❌ 无GPU → 检查是否有 -use-cpu 参数               │
│          ├─ ✅ 有 -use-cpu → 切换CPU模式（性能警告）      │
│          └─ ❌ 无 -use-cpu → 报错退出，拒绝启动          │
│  3. 节点RPC连接检查（强制）：                             │
│     ├─ 通过 RPC 连目标节点（本地 127.0.0.1:9331 或 远程IP:9331）│
│     ├─ 验证 RPC 认证（user/password）                    │
│     ├─ 检查区块链同步状态                                │
│     ├─ ✅ 连接成功且链已同步 → 继续                       │
│     └─ ❌ 连接失败 / 未同步 → 报错退出，不进入挖矿状态   │
│  4. 矿工通知已连接的节点："我已启动，请检测公网地址"       │
│  5. 节点(tkncd) 执行公网地址检测：                       │
│     ├─ 第1优先：IPv6 可用？→ 使用 IPv6 地址              │
│     ├─ 第2优先：IPv4 公网可达？→ 使用 IPv4 地址          │
│     ├─ 第3：UPnP/NAT-PMP 映射成功？→ 使用映射地址        │
│     └─ 都失败 → 标记"无公网地址"                        │
│  6. 节点将检测结果通过 P2P 网络 / RPC 上报给种子节点/Web   │
│  7. Web 服务器更新该矿工的卡片状态                      │
│                                                         │
│  结果：                                                  │
│  ├─ 有公网 IP/域名 → Web 显示 "在线 · 可调用" ✅         │
│  └─ 无公网 IP → Web 显示 "在线 · 不可调用(无公网)" ⚠️    │
│                                                         │
│  后续变更：                                              │
│  · 矿工每次重启都会重新自检并上报                         │
│  · 公网状态变化（如获得 IPv6）会在下次重启后自动更新      │
│  · 矿工也可在 Web 页面手动指定/修改公网地址或域名       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

#### 方法 1：节点自动检测（推荐，矿工启动时自动触发）

节点在矿工启动时自动按以下优先级检测：

| 优先级 | 检测方式 | 条件 | 结果 |
|--------|---------|------|------|
| 1 | IPv6 检测 | 系统 IPv6 接口可用且可路由 | 使用 IPv6 地址（无需 NAT 穿透） |
| 2 | STUN 检测 | 通过 STUN 服务器获取映射后的公网 IPv4 | 使用检测到的 IPv4 |
| 3 | UPnP/NAT-PMP | 路由器支持端口映射 | 使用映射后的公网地址 |
| 4 | P2P 中转 | 节点与种子节点有P2P连接 | 可通过 p2pinference RPC 调用（见方法3） |
| 5 | 全部失败 | 以上均不可用 | 标记"无公网"，Web 显示不可调用 |

#### 方法 2：手动指定（节点RPC命令 或 Web页面）

```powershell
# 通过节点RPC设置公网地址
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> setpublicip "203.0.113.50"

# 设置域名（推荐用于有域名的服务器）
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> setpublicip "my-node.example.com"
```

或通过 Web 页面：
1. 登录 Web 页面（钱包签名验证）
2. 进入"我的节点"设置页面
3. 输入公网 IPv4 / IPv6 地址或域名
4. **节点**签名验证后保存配置并上报

#### 无公网地址时的行为

- Web 服务器显示该矿工为 **"在线 · 不可调用（无公网地址）"**
- 用户无法通过 HTTP API 直连该矿工进行 LLM 推理调用
- 矿工仍然可以正常 PoW 挖矿（挖出的区块正常同步到全网）
- 一旦矿工获得公网地址（如开启 IPv6、配置端口转发、或手动指定域名），下次启动时会自动更新状态为"可调用"

#### 方法 3：P2P 直连推理（节点间端到端）

> 推理请求由**客户节点**通过 P2P 网络直接发送给**矿工节点**，二者端到端直连。种子服务器/Web **完全不参与**任何推理数据或信令的中转。

当客户节点通过 P2P 网络已与某个矿工节点建立连接时，可直接发起推理。无需 HTTP 网关、无需公网 IP 直连矿工的 9332 端口、无需经种子节点中转。

**核心原理**：

```
客户节点 ──P2P APIREQ(9333)──→ 矿工节点 ──localhost──→ 本地矿工(127.0.0.1:9332) → GPU推理
    ↑                                                                              │
    └──────────────────────── P2P APIRESP（内容+token计数）────────────────────────┘
```

**与 HTTP 网关方式的对比**：

| 对比项 | 方式A：节点公网IP网关 | 方式B：P2P 直连推理 |
|--------|----------------------|-------------------|
| 调用路径 | `http://[节点公网IP]:9313/v1/chat/completions` | `tknc-cli p2pinference` |
| 网络要求 | 节点必须有公网IP（IPv6/IPv4/UPnP） | 客户节点与矿工节点 P2P 已互通 |
| 适用场景 | 外部浏览器/HTTP 客户端调用 | 节点间互调、去中心化场景 |
| 调用方式 | HTTP REST API（OpenAI兼容） | 节点RPC命令 |
| 计费方式 | 先用后付（见 §5.3 步骤4） | 先用后付（同左，计费统一） |
| 中转 | 无（节点↔本地矿工 localhost） | 无（客户节点↔矿工节点 P2P 直连） |

**使用步骤**：

**步骤1：检查矿工在线**

```powershell
# 通过Web黄页确认矿工状态（只读展示，不参与后续推理）
$r = Invoke-RestMethod -Uri 'http://66.154.101.183/api/miners' -Method Get
# 确认目标矿工 status=online
```

**步骤2：在客户节点上查找目标矿工的 P2P peer_id**

```powershell
# 在【客户节点】本机查询已连接的 P2P peer 列表
tknc-cli -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcport=9331 getpeerinfo
# 返回JSON数组，找到目标矿工对应的peer id
# 示例: {"id": 672, "addr": "36.34.254.233:9333", "synced_blocks": 889, ...}
```

如何确认哪个peer是目标矿工：
- 看 `addr` 字段：目标矿工节点的公网地址（IPv4/IPv6）
- 看 `synced_blocks`：应该 > 0（已同步的节点）
- 如果只有一个peer，那就是目标矿工

**步骤3：通过 p2pinference RPC 发送推理请求**

```powershell
# 在【客户节点】本机执行，直接 P2P 发给矿工节点
tknc-cli -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcport=9331 p2pinference "模型名" "提示文本" <peer_id>

# 示例：推理2+2=?
tknc-cli -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcport=9331 p2pinference "qwen2.5-0.5b-instruct" "2+2=?" 672
```

**p2pinference 参数说明**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| model | string | 是 | 模型名称，如 `qwen2.5-0.5b-instruct` |
| prompt | string | 是 | 推理提示文本 |
| peer_id | numeric | 否 | 目标矿工节点 peer ID（省略则自动选第一个已连接的矿工节点） |
| api_key | string | 否 | API Key（用于握手校验+先用后付计费，省略则信任调用不计费） |

**返回值**：

```json
{
  "content": "2+2 equals 4.",
  "tokens_used": 180,
  "cost": 180,
  "peer_id": 672
}
```

| 字段 | 说明 |
|------|------|
| content | 推理结果文本 |
| tokens_used | 消耗的token数（由节点独立计算：prompt_tokens + completion_tokens，客户节点与矿工节点核对一致后的值） |
| cost | 累计费用（TKNC，未满1整数倍则暂不上链） |
| peer_id | 处理请求的矿工节点 peer ID（-1表示本机矿工节点） |

> **计费说明**：p2pinference 与 HTTP 网关调用共用同一套先用后付计费（见 §5.3 步骤4、§5.6）。握手校验通过后建立推理链路（✅ 已实现 — HTTP 网关路径，`tknc_setinferproxytarget` 自动执行），客户节点本地累记，每满1 TKNC发起链上转账给矿工。P2P 路径握手待实现。

#### 矿工可选：仅挖矿模式（不提供 LLM 推理）

如果矿工只想参与 PoW 挖矿、不想被远程调用 LLM 推理服务：

```powershell
# 启动时添加 -no-inference 参数
D:\TKNC\build_mingw\bin\tknc-miner.exe -wallet=你的钱包地址 -no-inference
```

效果：
- 矿工正常 PoW 挖矿，出块奖励照常
- 节点上报时标记该矿工为 `"mode": "pow_only"`
- Web 显示状态为 **"在线 · 仅挖矿（不提供推理）"**
- 用户无法选择该矿工进行 LLM 推理调用
- 矿工**不会**因收到 LLM 请求而中断 PoW 挖矿

> **默认行为**：不加 `-no-inference` → 同时支持 PoW 挖矿 + LLM 推理（按需自动切换）

#### 步骤 4：完整推理付费流程（7步，严格按顺序执行）

> **核心原则**：先用后付，不预付、不锁仓。推理先发生，按真实产出 token 计费。客户节点本地累记消费，每累计满 1 TKNC → 用户钱包直接转账到矿工钱包。资金从不曾停留在任何中间位置。无需创建专门的"付费钱包"——使用已有钱包即可。

```
┌─────────────────────────────────────────────────────────────┐
│          完整7步推理付费流程（严格按顺序执行）                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  步骤1: 矿工登录WEB → 设定兑换比例（如100TKNC=1M token）    │
│         ↓ 节点端 setminerprice RPC 存储                      │
│                                                             │
│  步骤2: 客户登录WEB → 找到矿工 → 查看兑换比例               │
│         ↓                                                    │
│  步骤3: 客户在节点创建API Key（指定消费上限，如100 TKNC）    │
│         ↓ createescrow RPC (建立消费上限)                     │
│                                                             │
│  步骤4: 客户解锁钱包（如已解锁则跳过）                       │
│         ↓ walletpassphrase RPC (标准钱包解锁)                │
│                                                             │
│  步骤5: 客户节点发起推理请求（携带API Key）                  │
│         ↓ 节点验证API Key + 检查钱包解锁状态                 │
│                                                             │
│  步骤6: ✅ 握手校验（设置代理时自动执行）                       │
│         ↓ tknc_setinferproxytarget → 矿工 /v1/chat/handshake    │
│         ↓ 微型推理→token核对→价格验证                            │
│         ↓ 节点独立计算 tokens_used = prompt_tokens +          │
│         ↓                     completion_tokens              │
│                                                             │
│  步骤7: 矿工执行推理 → 节点统计token → 自动计费             │
│         ↓ 每满1TKNC → 用户钱包自动转账给矿工（上链）         │
│                                                             │
│  关键规则（铁律）：                                          │
│  · 资金从不曾停留在任何托管合约中                            │
│  · Escrow（消费限额记录）存在 LevelDB 中，不锁仓            │
│  · 服务器崩溃、节点损坏不影响历史已上链的交易               │
│  · 未上链的消费最多损失 <1 TKNC                             │
│  · 不存在锁定、质押、退款——没消费就不付钱                   │
│  · API Key 仅记录消费上限，使用完自动停止                   │
│  · 无需创建专门的付费钱包——使用已有钱包即可                │
│  · 节点独立统计token（prompt_tokens + completion_tokens）    │
│  · 矿工不参与token统计和计费                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**推理前必须确认的事项**：

> ✅ 握手校验已实现（HTTP 网关路径）：`tknc_setinferproxytarget` 在设置代理时自动调用矿工的 `/v1/chat/handshake` 端点，执行微型推理核对 token 计数、验证兑换比例。

| # | 确认项 | 由谁确认 | 失败时 | 状态 |
|---|--------|---------|--------|------|
| 1 | 目标矿工在线且有公网地址 | Web 黄页展示 | ❌ 无法连接，提示"矿工不可达" | ✅ 已实现 |
| 2 | 矿工当前兑换比例已设定（WEB） | 节点握手校验计算真实兑换比例 | ❌ 握手失败，拒绝连接 | ✅ 已实现 |
| 3 | 客户已创建 API Key + 钱包已解锁 | 客户节点本地检查 | ❌ 提示"请先解锁钱包" | ✅ 已实现 |
| 4 | 钱包余额 ≥ 1 TKNC | 客户节点本地检查 | ❌ 提示"余额不足，请充值" | ✅ 已实现 |
| 5 | 双方 token 计数口径一致 | 握手校验核对 | ❌ 计数不一致，拒绝连接 | ✅ 已实现 |

**API Key = 消费上限凭证**：

```
客户获取 API Key 的流程：
1. 客户登录 WEB → 浏览矿工列表 → 查看矿工兑换比例
2. 客户选择目标矿工 → 输入指定消费 TKNC 总数额（如 100 TKNC）
3. 客户用钱包签名确认消费总额 → WEB 生成 API Key
4. API Key 绑定：消费上限 = 客户指定的 TKNC 总数额
5. 客户使用 API Key 开始推理 → 累计消费达上限 → 自动停止

关键：
· API Key 仅记录客户声明的消费上限，防止超额消费
· 每使用 1 TKNC 的 token → 用户钱包自动转账给矿工（实时上链）
· 使用完总额 → 自动停止推理
· 不存在退款——没消费就不付钱，已消费的已上链不可逆
```

**钱包操作（步骤4）**：

```
步骤4: walletpassphrase RPC — 解锁钱包（标准钱包操作）
       walletpassphrase "密码" 300  — 5分钟后自动锁定
       walletpassphrase "密码" 0    — 不自动锁定（需手动 walletlock）

注意：无需创建专门的付费钱包。系统直接使用已有钱包进行推理计费转账。
      只要钱包已加载且有足够余额，解锁后即可开始推理。
```

#### 步骤 4 补充：计费上链细节

```
推理中的计费流程（客户节点 + 矿工节点 双方对账）：

1. 矿工执行推理 → 逐 token 流式返回 → 节点统计 token 计数
2. 客户节点：用同款 tokenizer 独立计数 + 本地累记消费
3. 客户节点本地累记消费 = tokens × rate_tknc_per_token
4. 累计达 1 TKNC 整数倍 → 客户钱包 sendtoaddress(矿工钱包, 1) → 交易上链
5. 矿工节点：检查链上是否收到转账 → 未收到则中断推理

每次推理后客户节点本地状态变化：
  推理前: 累计消费 0.0 TKNC
  推理1:  累计消费 0.3 TKNC（未满1，不上链）
  推理2:  累计消费 0.8 TKNC（未满1，不上链）
  推理3:  累计消费 1.2 TKNC → 上链1 TKNC → 剩余0.2 TKNC
  推理4:  累计消费 0.7 TKNC（未满1，不上链）
  推理5:  累计消费 1.1 TKNC → 上链1 TKNC → 剩余0.1 TKNC
```

### 5.4 推理会话生命周期

> 推理会话由握手校验建立（✅ 已实现 — HTTP 路径），由双方对账维持，由链上转账结算。

```
推理会话生命周期：

1. 握手校验阶段（✅ 已实现 — HTTP 路径）
   客户节点 → 矿工节点: POST /v1/chat/handshake
   矿工节点 → 客户节点: handshake response (含test_tokens + 真实兑换比例 + token_verification)
   客户节点核对: token计数一致 + 兑换比例匹配 + 用户确认
   ├─ 通过 → 建立推理会话
   └─ 不通过 → 拒绝连接

2. 推理执行阶段
   客户节点 → 矿工节点: INFER_REQ
   矿工: 执行推理 → 逐token流式返回 → 节点统计计数
   客户节点: 独立计数 + 核对 + 本地累记消费
   每满1 TKNC: 客户钱包 → sendtoaddress(矿工钱包, 1) → 上链

3. 会话结束
   · 推理完成 → 双方计数最终核对 → 会话正常结束
   · 计数偏差超阈值 → 中断推理 → 上报异常
   · 矿工离线 → 客户节点检测超时 → 会话异常结束
   · 客户钱包余额不足 → 客户节点主动中断 → 未上链消费 <1 TKNC 损失
```

### 5.5 模型注册（Model Registry — 防作弊核心）

> 矿工在提供 LLM 推理服务前，必须注册模型能力。目标节点在每次推理前校验模型 hash。

**注册信息（Model Registry）**：

```
{
  "model": "qwen2.5-0.5b-instruct",
  "hash": "sha256:abc123def456...",     // GGUF 文件 SHA256
  "size_mb": 468,
  "loaded": true,                        // 当前是否已加载
  "gpu_capability": "P106-100",          // 或 "CPU"
  "publisher": "token1miner...",
  "registered_at": 1717772800
}
```

**校验规则**：
- 推理请求到达 → 目标节点校验快照中的 `model_hash` 与矿工注册的 `hash` 是否一致
- 不一致 → 拒绝请求，不转发给矿工
- 一致 → 转发请求，执行推理

### 5.6 计费系统（双方对账 + 实时上链 — 客户节点付费，矿工节点核对）

> **核心原则**：客户节点是付费方（自己记账防多扣），节点统计token输出量（权威计数）。节点统计+客户核对、每满1 TKNC链上转账。Web不参与任何计费。矿工只做推理，不参与token统计和计费。

**计费流程**：

```
推理请求
    ↓
客户节点发起握手校验（✅ 已实现 — `tknc_setinferproxytarget` 自动调用矿工 `/v1/chat/handshake`）
    ↓ 节点计算矿工真实兑换比例 + 微型推理核对
    ↓
握手通过 → 建立推理链路
    ↓
矿工执行推理 → 逐token流式返回 → 节点统计token计数
    ↓
客户节点：
  · 用同款tokenizer独立计数
  · 与节点计数核对（偏差超阈值 → 中断推理）
  · 本地累记消费 = tokens × rate
    ↓
累计满1 TKNC？
├─ 是 → 客户钱包 sendtoaddress(矿工钱包, 1) → 交易上链
└─ 否 → 继续累记
    ↓
矿工节点：检查链上是否持续收到转账
├─ 收到 → 继续推理
└─ 连续N次未收到 → 中断推理
```

**计费公式**：

```
cost_tknc = tokens_used × rate_tknc_per_token
```

> 其中 `rate_tknc_per_token` 来自节点在握手校验中计算的真实兑换比例（不依赖Web展示，防篡改）。✅ 已实现 — 握手端点从 LevelDB 读取矿工通过 `setminerprice` RPC 设置的真实价格。

**❌ Web 禁止做**：
- token 计算
- 余额管理
- 扣费操作
- 退款操作
- 持有钱包私钥

### 5.7 先用后付模式下的资金安全

> **核心原则**：先用后付模式下不存在退款需求——没消费就不付钱，已消费的已上链不可逆。

**资金安全保障**：

| 风险场景 | 保护机制 | 最大损失 |
|---------|---------|---------|
| 服务器崩溃 | 已上链交易不受影响；未上链消费 <1 TKNC | <1 TKNC |
| 节点损坏 | 客户钱包私钥在本地，不受影响 | <1 TKNC（未上链部分） |
| 矿工中途断线 | 客户节点检测超时，停止累记 | <1 TKNC（未上链部分） |
| 矿工恶意不推理 | 握手校验失败 → 拒绝连接（✅ 已实现） | 0 TKNC |
| 矿工篡改兑换比例 | 节点握手校验计算真实兑换比例，标价≠实价弹窗警告（✅ 已实现） | 0 TKNC（用户可拒绝） |
| 客户恶意不付款 | 矿工检查链上转账，未收到则中断推理 | <1 TKNC（矿工损失） |

**矿工防客户白嫖**（⚠️ 待实现）：
- 矿工在推理中实时检查链上转账
- 连续 N 次应付款但未收到 → 中断推理
- 最大风险 = 1 TKNC（客户在满1 TKNC前断连）

**客户防矿工多扣**：
- 客户节点独立计数，以节点统计为准（矿工不参与token统计）
- 计数偏差超阈值 → 中断推理
- 资金由客户钱包私钥控制，不经任何第三方

### 5.8 异常处理（推理失败 / 矿工故障）

#### 推理失败时的计费规则

| 失败类型 | 是否扣费 | 说明 |
|---------|---------|------|
| 矿工返回 HTTP 错误（500/502/503） | **❌ 不扣费** | 服务端错误，用户无过错 |
| 矿工超时未响应（>86400秒） | **❌ 不扣费** | 矿工不可用 |
| 矿工 OOM / 崩溃 | **❌ 不扣费** | 矿工自身问题 |
| 模型加载失败 | **❌ 不扣费** | 矿工配置问题 |
| 模型 hash 不匹配 | **❌ 不扣费 + 拒绝请求** | 矿工可能换了模型 |
| 用户请求格式错误（400） | **❌ 不计费** | 请求无效 |
| **推理成功返回结果** | **✅ 按 output_tokens 扣费** | 只统计成功返回的 token 数 |

> **扣费时机**：仅在矿工**成功返回非空推理结果**后客户节点才累加本地消费。中途失败/空结果一律不计费。

#### 矿工在服务期间下线的处理

1. 目标节点检测到本地矿工断开连接
2. 目标节点通过 P2P 通知种子节点/Web："矿工离线"
3. Web 标记该矿工状态为 OFFLINE
4. 推理会话标记为异常（矿工离线）
5. 客户节点停止累记消费
6. 未上链消费 <1 TKNC（客户最大损失）

### 5.9 并发控制（防止超额消费）

> **问题**：客户节点同时发多个推理请求，如果不控制并发，可能在不知情的情况下超额消费。

#### 解决方案：客户节点本地消费上限 + 串行推理

```
客户节点为每次推理会话设置消费上限：

推理会话控制逻辑:
  1. 客户节点设置单次推理最大消费上限（如 10 TKNC）
  2. 推理中实时累记消费，达到上限 → 中断推理
  3. 每满1 TKNC → 链上转账 → 矿工确认收到
  4. 矿工连续N次未收到转账 → 矿工中断推理
     
效果:
  · 客户节点控制消费上限，不可能超额
  · 矿工通过链上转账确认控制风险，不可能被白嫖超过1 TKNC
  · 双方都有中断推理的权力
```

#### 步骤 5：调用 LLM 推理（客户节点直连矿工节点）

```bash
# 方式 A：通过客户节点直连矿工节点（推荐 — 端到端直连）
# 前提：客户节点已通过握手校验与矿工节点建立推理链路（✅ 已实现 — tknc_setinferproxytarget 自动执行握手）
tknc-cli -rpcuser=tkncadmin -rpcpassword=<RPC密码> -rpcport=9331 \
  p2pinference "qwen2.5-0.5b-instruct" "Hello, who are you?"
```

**请求处理流程（关键 — 客户节点直连矿工节点，不经Web中转）**：

```
1. 客户节点从 Web 黄页获取矿工节点公网地址（仅展示，Web不参与后续）
2. 客户节点发起握手校验（✅ 已实现 — `tknc_setinferproxytarget` → `/v1/chat/handshake`） → 节点返回test_tokens + 真实兑换比例 + token_verification
3. 客户节点核对：token计数一致 + 兑换比例匹配 + 用户确认（✅ 已实现 — CLI 显示握手结果并警告不一致）
4. 握手通过 → 客户节点通过 P2P(9333) 直连矿工节点（⚠️ P2P 路径握手待实现，HTTP 路径已实现）
5. 矿工节点转发到本地矿工(127.0.0.1:9332)
6. 矿工执行推理 → 逐token流式返回 → 节点统计token计数
7. 客户节点：独立计数 + 核对 + 本地累记消费
8. 每满1 TKNC → 客户钱包 sendtoaddress(矿工钱包, 1) → 交易上链
9. 矿工节点检查链上转账 → 未收到则中断推理
```

#### 步骤 6：消费上限控制

```
触发条件：客户节点本地累记消费达到设定的最大消费上限

例如：
· 客户节点设置本次推理最大消费 10 TKNC
· 推理中实时累记消费
· 累计消费达到 10 TKNC 时
→ 客户节点自动中断推理
→ 返回 {"error": "Cost limit reached", "cost": 10.0, "max_cost": 10.0}
→ 客户可重新发起推理（设置新的消费上限）
```

### 5.10 API 请求/响应规范

**请求体**：

```json
{
  "messages": [                            // 必需 - 消息列表
    {"role": "user", "content": "..."}
  ],
  "stream": true,                          // 可选 - 系统统一为逐字流式输出，始终为 true（SSE）
  "max_tokens": -1,                        // 可选 - 最大生成 token 数（-1=无限/直到EOS，>0=指定数量，默认 -1）

```

> **stream 说明**：本系统统一为逐字流式输出（SSE），无论客户端是否指定 `stream: true`，系统始终使用 SSE 流式转发。矿工始终使用 `GenerateStream()` 逐 token 生成，网关始终使用 SSE `text/event-stream` 转发。不存在非流式路径。

> **max_tokens 说明**：本系统是桥梁，不限制生成长度。`-1` 表示无限生成（直到模型自然输出 EOS），由矿工硬件性能决定实际输出速度和长度。客户端也可指定具体数值（如 4096）来限制生成长度。该参数从客户端全链路透传到矿工 LLM 引擎，无任何人造截断。

### 5.11 Token 计费标准

| 项目 | 说明 |
|------|------|
| **定价权** | 矿工登录WEB设定兑换比例（如 1 TKNC = 1M tokens），节点在握手校验中计算真实兑换比例并返回给客户（✅ 已实现 — 从 LevelDB 读取 `setminerprice` 设置的价格） |
| **定价验证** | 客户节点从握手校验获取矿工实价，与Web标价核对，不一致则弹窗警告（✅ 已实现 — `expected_price` 参数比较） |
| **计费方式** | 先用后付：推理先发生，客户节点本地累记消费，每满1 TKNC链上转账 |
| **计费单位** | per token（每个输出 token 按握手校验获取的比率折算为 TKNC）（✅ 已实现 — 握手返回 `verified_price_per_1m_tknc`） |
| **统计位置** | **节点统计**：节点统计token输出量，客户节点独立核对（防多扣）。矿工不参与token统计 |
| **核对机制** | 每个流式token包中节点附带累计计数，客户节点独立计数核对，偏差超阈值中断推理 |
| **上链频率** | 每累计满 1 TKNC → 客户钱包直接链上转账给矿工钱包 |
| **Web/种子角色** | **仅做黄页展示** — 不碰任何token计量、余额、扣费、退款 |

> ⚠️ **统一标准**：无论用户通过 P2P 还是 HTTP 网关调用推理，Token 计费都遵循同一套先用后付+实时上链模型。定价来自握手校验直接获取（✅ HTTP 路径已实现，⚠️ P2P 路径待实现），不依赖Web展示。

### 5.13 定价机制（握手校验直接获取 + 防篡改核对）

```

        例：1 TKNC = 1,000,000 tokens
        → 存入 Web 数据库作为"标价"

Step 3: 客户节点发起握手校验（HANDSHAKE_REQ）
        → 矿工节点返回 HANDSHAKE_RESP {
            test_tokens: [...],

        }

        ├─ Web标价 = 矿工实价 → ✅ 正常
        └─ Web标价 ≠ 矿工实价 → ⚠️ 弹窗警告用户

Step 5: 推理中计费（客户节点本地执行）
        每次推理：
        1. 客户节点独立计数 tokens
        2. 本地累记消费 = tokens × rate（rate 来自握手校验）
        3. 累计满1 TKNC → 客户钱包 sendtoaddress(矿工钱包, 1) → 上链
```

## 六、P2P LLM 推理（节点间直接通信）

> P2P LLM 推理通过已有的 P2P 网络发送推理请求，**请求从一个节点发出，由目标节点的本地矿工执行**。不需要 HTTP 服务器中转、不需要公网 IP 直连矿工。

### 6.1 架构说明

- **请求方节点**：用户连接的节点（可以是本地节点或远程节点），通过 P2P 发送推理请求。
- **服务方节点**：运行着矿工的节点，接收 P2P 请求后转发给本地矿工执行。
- **矿工**：在服务方节点的 localhost 上执行实际推理，结果原路返回。
- **通信**：通过 P2P 端口（默认 9333）传递 APIREQ（请求）和 APIRESP（响应）消息。
- **RPC 命令**：`p2pinference` — 请求方节点用它发送推理请求。

### 6.2 与 Web 调用的对比

| 维度 | P2P 节点间推理 | HTTP 网关调用 |
|------|---------------|-------------|
| 通信方式 | P2P 消息 (apireq/apiresp) | HTTP REST API（OpenAI兼容） |
| 认证 | 握手校验（⚠️ P2P 路径待实现） | 握手校验（✅ 已实现 — `tknc_setinferproxytarget`） |
| 是否经过Web | 否（客户节点↔矿工节点 直连） | 否（客户端→矿工节点公网IP:9313 直连） |
| 适用场景 | 节点间互调、去中心化 | 外部浏览器/HTTP客户端调用 |

> **关键统一**：无论 P2P 还是 HTTP 网关调用，**Token 计量都是双方独立计数+实时核对**，定价都来自握手校验直接获取（✅ HTTP 路径已实现，⚠️ P2P 路径待实现），计费都是先用后付+每1TKNC链上转账。Web 不参与任何 token 计量或计费。

#### 第五步：发送 P2P 推理请求

在 Node2 终端输入：

```

```

例如：

```
tknc-cli.exe -rpcport=19331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> p2pinference "qwen2.5-0.5b-instruct" "What is 1+1?"
```

**内部执行流程**：

1. Node2 构造 APIRequest → 通过 P2P 发送到 Node1
2. **Node1（节点）**接收请求 → 转发到**本地矿工**(127.0.0.1:9332)
3. **矿工**从 PoW 模式切换到 LLM 模式 → 执行推理
4. **矿工**返回结果 + prompt_tokens + completion_tokens → **切回 PoW 模式**
5. **Node1（节点）**独立计算 tokens_used = prompt_tokens + completion_tokens → 将 APIResponse 通过 P2P 发回 Node2
6. Node2 显示结果

终端返回推理结果，包含：

- `content` — 推理生成的文本
- `tokens_used` — 消耗的 token 数（由节点独立计算：prompt_tokens + completion_tokens，矿工节点与客户节点核对一致）
- `cost` — 费用（TKNC），计算公式为 **`output_tokens × rate_tknc_per_token`**（rate 来自握手校验获取的真实兑换比例，详见 §5.13；✅ 已实现 — HTTP 路径）
- `peer_id` — 处理请求的节点 ID

#### 第六步：停止节点

先停 Node2：

```
tknc-cli.exe -rpcport=19331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> stop
```

再停 Node1：

```
tknc-cli.exe -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<RPC密码> stop
```

### 6.5 p2pinference 命令参数

| 参数位置 | 名称 | 类型 | 必需 | 说明 |
|---------|------|------|------|------|
| 第 1 个 | model | 字符串 | 是 | 模型名称 |
| 第 2 个 | prompt | 字符串 | 是 | 推理提示词 |
| 第 3 个 | peer_id | 数字 | 否 | 目标节点 ID，省略时自动选择 |

> **两种调用模式**：
> - 有 `max_cost` → 走先用后付计费模式（客户节点本地累记，每满1 TKNC链上转账）
> - 无 `max_cost` → P2P 节点间信任调用（免费，调试/测试用）

### 6.6 常见错误与解决

| 错误提示 | 原因 | 解决 |
|---------|------|------|
| No connected peer found | Node2 没有连接到 Node1 | 检查 Node2 的 connect 配置是否正确 |
| timed out after 86400 seconds | 推理超时（24小时） | 检查 Node1 的矿工是否正常（127.0.0.1:9332可达） |
| PeerManager not available | 节点内部错误 | 重启 tkncd |
| Connection refused to miner | Node1 无法连到矿工 | 检查矿工是否启动、是否监听在 127.0.0.1:9332 |

### 6.7 P2P 推理数据流（含模式切换）

当通过 `p2pinference` 发送请求时，系统内部执行以下流程：

1. 请求方节点构造 APIRequest（包含模型名、提示词、请求 ID、防重放 nonce）
2. 通过 P2P 网络发送 APIREQ 消息到**目标节点**
3. **目标节点**接收后验证请求
4. **目标节点**将请求转发到**本地矿工**（127.0.0.1:9332）
5. **矿工**从 PoW 模式 **切换** 到 LLM 推理模式
6. **矿工**调用本地模型执行推理（temperature=0.1, 最多 256 token）
7. **矿工**返回结果 + 输出 token 数量 → **切换回 PoW 模式**
8. **客户节点**独立计数 + 与节点计数核对
9. **客户节点**本地累记消费 = tokens × rate（rate 来自握手校验，✅ 已实现 — HTTP 路径；⚠️ P2P 路径待实现）
10. 累计满1 TKNC → 客户钱包 sendtoaddress(矿工钱包, 1) → 交易上链
11. **目标节点**将 APIResponse（内容、双方token计数、费用）通过 P2P 发回请求方节点
12. 请求方节点接收结果并显示

> 本节描述当前实际运行的 Web 评论系统。
>
> **⚠️ 支付机制说明（与推理支付的关系）**：
> 评论系统的 10 TKNC 支付使用**简单转账**（`sendtoaddress`），不需要包含定价元数据。
> 这是因为评论是一次性固定费用，不存在"按量计费"的需求。

### 7.1 评论权限矩阵（核心规则）

| 场景 | 付款方 | 收款方 | 删除权限 | 说明 |
|------|--------|--------|---------|------|

| 矿工邀请用户评论 (miner_pays_user) | 矿工 | 用户 | ✅ **矿工可删** | 矿工花了钱，有权删除 |
| 无关用户 | 无 | 无 | ❌ **看不到按钮** | 无交互关系 |
| 未登录用户 | 无 | 无 | ❌ **无权限** | 需登录 |

### 7.2 评论资格检查

**用户评论矿工的前提条件**：

1. ✅ 用户已登录 (session_token — 钱包签名验证)

**矿工邀请评论的前提条件**：

2. ✅ 矿工支付 10 TKNC 给目标用户地址

## 九、TKNC 排放完毕后的安全维护

> 当 TKNC 全部排放完毕（达到预设总量上限），矿工的角色从"挖矿+推理"转变为"纯安全维护"。

### 9.1 排放完毕标志

- 区块高度达到预设总量上限
- Coinbase 出块奖励降为 **0**（不是"或仅为交易手续费"——出块奖励和交易手续费是两个独立概念）
- 网络共识：所有节点确认排放完毕

### 9.2 矿工行为转变

```
┌─────────────────────────────────────────────────────────┐
│              排放完毕前后矿工行为对比                     │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  排放完毕前：                                            │
│  · 默认 PoW 挖矿（获取 Coinbase 奖励）                  │
│  · 被调用时切换到 LLM 推理（赚取 TKNC）                  │
│  · 两种收入来源                                         │
│                                                         │
│  ══════════════════════════════════════════════════    │
│                                                         │
│  排放完毕后：                                            │
│  · ❌ PoW 出块尝试停止（Coinbase 奖励降为0，无经济激励）   │
│  · ✅ LLM 推理继续（赚取手续费）                         │
│  · ✅ 全节点验证继续（被动接收+验证新区块，维护网络安全） │
│  · ✅ 交易确认继续（维护账本一致性）                     │
│  · ✅ 交易手续费可赚取（作为验证节点的收入）             │
│  · 待命状态：随时准备接收 LLM 推理任务                   │
│                                                         │
│  > 关键理解：停止"出块"(主动计算nonce) ≠ 停止"验证"(被动检查)│
│  > 类比：停止生产商品，但继续检查别人生产的商品质量       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 9.3 安全维护职责

即使没有新的 TKNC 产出，运行中的矿工/节点仍然对网络安全至关重要：

| 职责 | 说明 | 是否持续 |
|------|------|---------|
| 区块验证 | 验证新区块的有效性（由节点执行） | ✅ 是 |
| 交易广播 | 转发交易到全网（由节点执行） | ✅ 是 |
| 共识参与 | 投票/签名确认链状态（由节点执行） | ✅ 是 |
| LLM 推理 | 响应用户请求赚取手续费 | ✅ 按需 |
| P2P 连接 | 维护网络拓扑（由节点执行） | ✅ 是 |

### 9.4 经济模型转变

```
排放完毕前：
  收入 = Coinbase奖励(PoW) + LLM推理费

排放完毕后：
  收入 = LLM推理费 + 交易手续费分成(如有)
```

### 10.4 本地推理代理（IDE IPv4 兼容）

> **背景**：很多 IDE 工具（VSCode、Cursor、JetBrains 等）不支持 IPv6 地址。当矿工只有 IPv6 公网地址时，IDE 无法直接连接。本地节点自动启动 IPv4 代理，将 IDE 的 IPv4 请求转发到矿工的 IPv6 地址。

#### 工作原理

```
IDE (IPv4) → 127.0.0.1:9393 (本地代理) → [矿工公网IP]:9313 (矿工API Gateway)
     ↑                                          ↑
  IPv4 地址                               IPv4 或 IPv6 均可
  所有 IDE 兼容                            代理自动识别协议
```

- **代理自动启动**：节点启动时代理自动在 `127.0.0.1:9393` 监听，**无需任何启动参数**
- **目标动态设置**：代理启动时不知道任何矿工信息，用户通过 CLI 输入矿工 IP + API Key 后动态设置
- **全程点对点**：代理仅本地转发，Web 服务器不参与任何数据转发
- **端口可配置**：通过 `tknc.conf` 中 `-inferproxyport` 配置，默认 9393

## 附录 A：目录结构说明

### 原则：程序在哪，数据就在哪

TKNC 系统遵循**"数据跟随可执行程序"**原则：如果节点程序(`tkncd.exe`)在 A 文件夹，那么模型、区块数据、钱包都应该在 A 文件夹下创建对应的子目录。

### 标准目录布局

```

├── build\                         # 编译产物 + 运行时（节点和矿工的工作目录）

│   │   ├── tknc-miner.exe       # 矿工程序
│   │   └── tknc-cli.exe         # 命令行工具
│   ├── data\                     # 节点运行时数据
│   │   ├── tknc.conf            # 节点配置文件
│   │   └── mainnet\             # 区块链数据
│   │       ├── blocks\          # 区块文件
│   │       └── chainstate\      # 链状态
│   └── models\                   # AI 模型文件
│       └── models\
│           └── qwen2.5-0.5b-instruct.gguf  # LLM模型(468MB)
│
├── data\                          # 用户钱包和备份数据
│   └── backups\                  # 钱包备份

├── TKNC\                          # 源代码（不参与运行）

```

### 启动参数与目录对应关系

| 程序 | 关键参数 | 指向目录 | 用途 |
|------|---------|---------|------|
| 节点(tkncd) | `-datadir=D:\TKNC\build\data` | `build\data\` | 区块链数据、配置 |
| 矿工(miner) | `-wallet=xxx`（必填） | `build\models\` | AI 模型文件（由节点RPC下发路径） |

> - **节点连接检查**：启动时必须能连上节点RPC(9331)，否则不进入挖矿状态

## 附录 B：常见问题排查

### Q1：RPC 连接失败 (network/stats 返回 block_height=0)

**症状**：矿工启动正常，但 API 返回的数据与节点实际状态不符。

**原因**：PowerShell 参数解析截断 IP 地址。

**解决**：使用引号包裹 IP 地址参数：

```powershell
# ❌ 错误
-rpcconnect=127.0.0.1

# ✅ 正确
"-rpcconnect=127.0.0.1"
```

**验证方法**：观察矿工启动日志，确认显示：

```
[PARAM] rpcConnect='127.0.0.1' length=9  ← 必须是length=9而非3
```

### Q2：矿工必须绑定 127.0.0.1:9332（仅本地！节点转发）

**正常状态**：`netstat -ano` 显示矿工监听在 `127.0.0.1:9332`。

**说明**：这是**正确的预期行为**！矿工绑定 `127.0.0.1:9332` 仅允许本机节点通过localhost访问。外部用户通过**节点的 API Gateway(:9313)** 调用推理服务（不是直连矿工）。公网地址由节点管理。

**如果看到 0.0.0.0:9332 而非 127.0.0.1:9332**：
- 矿工代码中 bind 地址配置错误（安全漏洞！）
- 检查源码中的 bind 地址是否为 `127.0.0.1`
- 重新编译矿工
- 验证：`netstat -ano | findstr "127.0.0.1.*9332"`

### Q3：矿工仍然需要 -model 参数？

**症状**：启动时报错 "model path required" 或类似错误。

**原因**：使用的旧版矿工程序，尚未升级到节点RPC下发模型路径。

**解决**：
1. 重新编译最新版矿工代码（移除 -model 必填检查）
2. 确保节点已配置模型路径（通过 RPC 或配置文件）
3. 使用新版启动命令：`tknc-miner.exe -wallet=xxx`

### Q4：无 GPU 环境如何启动矿工？

**症状**：启动时报错 "No GPU available. Add -use-cpu to force CPU mode."

**原因**：GPU优先原则 — 矿工默认仅使用GPU，检测不到GPU时拒绝启动。

**解决**：
- **推荐方案**：安装 NVIDIA/AMD GPU 及驱动（CUDA / Vulkan / OpenCL）
- **备选方案**（性能较差）：启动时加 `-use-cpu` 参数强制CPU模式
  ```
  tknc-miner.exe -wallet=xxx -use-cpu
  ```
- ⚠️ CPU模式下PoW挖矿速度和LLM推理速度都会显著降低

### Q5：连远程节点挖矿怎么配置？

**症状**：想在机器B上跑矿工，但节点和P2P网络在机器A上。

**解决**：使用 `-rpcconnect` 参数指定远程节点IP。示例：
```
# 机器B上的矿工，连接机器A(192.168.1.100)上的节点
tknc-miner.exe -wallet=xxx "-rpcconnect=192.168.1.100" -rpcport=9331 -rpcuser=tkncadmin -rpcpassword=<远程节点的RPC密码>
```

**关键检查**：
1. 远程节点必须开启 `-server=1` 并监听 9331 端口
2. 防火墙放行 9331 端口（仅限内网/指定IP，**禁止对公网开放**，见 Q7）
3. `-rpcuser` / `-rpcpassword` 必须与远程节点配置一致
4. 矿工启动日志需显示 `[Node] Connected. Block height: N` 才算正常

> ⚠️ **安全提示**：种子服务器（66.154.101.183）的 RPC 端口 9331 已于 2026-07-07 加固为仅允许 localhost 访问（见 Q7），外部矿工无法通过公网 RPC 连接种子节点。外部矿工应通过 P2P 端口 9333 连接种子节点。

### Q6：更新节点后区块浏览器和 AI 市场不显示数据（RPC 认证不匹配）

**症状**：前端显示 "Error loading blocks"，API 返回 `RPC Parse Error: Unexpected end of JSON input`。

**原因**：`tknc.conf` 中 `rpcuser`/`rpcpassword` 被注释或缺失，节点回退到 cookie 认证，与 Web 服务器的用户名/密码认证不兼容，返回 HTTP 401 + 空响应体。

**修复**：确保 `tknc.conf` 中 `rpcuser`/`rpcpassword` 未被注释，且与 Web 服务器 `.env` 中的 `TKNC_RPC_USER`/`TKNC_RPC_PASS` 一致。重启节点时必须使用 `-conf` 参数显式指定配置文件路径。

**预防**：部署新节点后检查配置文件；使用 systemd 管理进程。

### Q7：RPC 端口安全加固

**问题**：`tknc.conf` 曾配置 `rpcallowip=0.0.0.0/0` + `rpcbind=0.0.0.0`，将 RPC 端口暴露到公网，配合公开的弱密码可被远程调用任意 RPC 命令。

**修复**：三层防御 — ① `rpcbind=127.0.0.1` 限制仅本地监听；② iptables 防火墙兜底；③ 更换为 32 位随机密码。修复后 RPC 端口仅本地可达。

> 外部矿工应通过 P2P 端口 9333 连接种子节点，而非 RPC 端口 9331。

---

### Q8：区块浏览器地址查询失败（AddressIndex）

**问题**：地址查询依赖 `scantxoutset` 全量扫描 UTXO 集合，链增长后超时。

**修复**：新增 `AddressIndex` C++ 索引组件（LevelDB 存储），`getaddressutxos` RPC 从 O(n) 降至 O(k)。在 `tknc.conf` 中启用：`addressindex=1`。Web 服务器优先使用 `getaddressutxos`，回退 `scantxoutset`。

> `addressindex` 与 `-prune`（修剪模式）不兼容。

---

### Q9：nginx 代理缓冲导致大响应截断

**问题**：nginx 反向代理缓冲大 JSON 响应时，缓冲目录权限不匹配导致写入失败、响应截断。

**修复**：`chown -R www-data:www-data /var/lib/nginx/proxy/`；nginx 配置中 `proxy_buffering off`。

### Q10：统一流式输出 + 移除人造瓶颈（桥梁架构）

**核心理念**：系统是桥梁，不限制推理能力。输出速度取决于矿工硬件，不应有人为限制。

**关键变更**：

| 项目 | 改造前 | 改造后 |
|------|--------|--------|
| 所有超时 | 120-300 秒 | 86400 秒（24h） |
| Token 生成上限 | 8192 硬编码 | 无限制（-1 = 直到 EOS） |
| 默认 n_ctx | 2048/4096 | 131072（128K，可通过 `-n_ctx` 配置） |
| max_tokens | 不解析，硬编码 256 | 全链路透传，-1=无限 |
| 流式输出 | 仅 HTTP Gateway 支持 | 全路径统一 SSE 流式（无例外） |
| 请求体限制 | 1MB | 100MB |
| 缓冲区 | 固定 32KB/64KB | 动态增长（4KB 循环 recv） |

**影响文件**：`inference_gateway.cpp`, `net_processing.cpp`, `local_backend.cpp`, `llm_inference.h/cpp`, `loader.cpp`, `api_server.h/cpp`, `tknc-miner.cpp`, `api_protocol.h/cpp`, `p2p_llm.h/cpp`, `rpc/net.cpp`, `web/AI/server.js`, `web/AI/public/index.html`, `web/main/server.js`
