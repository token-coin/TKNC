## 一、关键架构事实（不可变，禁止幻觉）

### 1.1 三层架构与端口绑定

```
外部客户端 → 节点(:9313 API Gateway) → 本地矿工(127.0.0.1:9332) → GPU推理
     ↑              ↑                        ↑
  公网IPv6:9313   [::]:9313              仅127.0.0.1:9332
```

**铁律**:
- **节点9313端口只监听IPv6 `[::]:9313`，不监听IPv4 `0.0.0.0:9313`**
- **矿工9332端口只监听 `127.0.0.1:9332`，绝不对外**
- **外部调用必须使用IPv6地址，`127.0.0.1:9313` 永远连接不上！**

### 1.2 三种IP地址绝对不能搞混

| 地址 | 用途 | 禁止 |
|------|------|------|
| 139.196.28.21 | 种子服务器（只做矿工展示，不提供API！） | 禁止当作推理endpoint |
| 节点公网IPv6 | 提供OpenAI兼容HTTP API(:9313) | 禁止用127.0.0.1:9313 |
| 127.0.0.1:9332 | 矿工（仅本地，绝不对外） | 禁止绑定0.0.0.0 |

### 1.3 数据流铁律

```
阶段1: 发现矿工 → 种子服务器(139.196.28.21) Web页面
阶段2: 支付+获取Key → 种子服务器创建Key → P2P同步到全网节点
阶段3: 远程推理 → 节点公网IPv6:9313 → 节点转发到127.0.0.1:9332 → 矿工GPU推理
阶段4: 统计汇报 → 节点P2P广播
```

### 1.4 7900XT机器是Windows系统

- **不是Linux！不是Linux！不是Linux！**
- 需要Windows版tkncd.exe，不需要Linux ELF
- 编译用MinGW，不需要WSL交叉编译

### 问题1: 节点9313端口只监听IPv6，不监听IPv4

**发现过程**:
- 测试 `http://127.0.0.1:9313/v1/chat/completions` → 连接失败
- 测试 `http://[::1]:9313/v1/chat/completions` → 成功(404)
- `netstat -an` 确认: `TCP [::]:9313 LISTENING`，无 `0.0.0.0:9313`

**根因**: 节点的API Gateway绑定到 `[::]`（IPv6 any-address），不绑定 `0.0.0.0`（IPv4 any-address）

**影响**: 所有使用 `127.0.0.1:9313` 或 `localhost:9313` 的测试都会失败

**解法**: 使用IPv6地址调用推理API:
- `http://[::1]:9313/v1/chat/completions` (本机)
- `http://[2408:8244:bb00:6ad:...]:9313/v1/chat/completions` (远程)

**教训**: 测试推理时**必须使用IPv6地址**，禁止使用127.0.0.1或localhost

### 问题2: Gateway响应解析——矿工返回`response`字段，Gateway查找`content`字段

**发现过程**:
- 7900XT远程推理成功返回，但答案字段显示整个矿工JSON嵌套在content中
- 原始响应: `"content": "{\"response\":\"2+2 equals 2.\",\"tokens_used\":180,...}"`
- 期望响应: `"content": "2+2 equals 2."`

**根因**: `inference_gateway.cpp` L592-595:
```cpp
// 旧代码：只查找content字段
std::string content = miner_json.getString("content");
if (content.empty() && !miner_response.empty()) {
    content = miner_response;  // 整个JSON被当作content！
}
```
矿工返回的JSON格式是 `{"response":"...", "tokens_used":N, ...}`，没有`content`字段。
Gateway找不到`content`，就把整个矿工JSON当作content嵌套进OpenAI格式。

**修复**: `inference_gateway.cpp` L592-595:
```cpp
// 新代码：先查找response，再查找content
std::string content = miner_json.getString("response");
if (content.empty()) content = miner_json.getString("content");
```

**验证**: 本机RTX3070推理返回纯文本 "2+2 is 4." ✅（不再嵌套JSON）

**附带修复**: L602 拼写错误 `"minier_error"` → `"miner_error"`

### 问题3: Web服务器MINER_TIMEOUT过短导致矿工显示offline

**发现过程**:
- Web API返回 `"status": "offline"`, `"online": 0`
- 但矿工实际在运行

**根因**: `server.js` 中 `MINER_TIMEOUT = 5000` (5秒)，但节点心跳间隔=15秒
- 矿工在5秒后被标记为offline，但心跳每15秒才发一次

**修复**: `server.js` L149-153:
```javascript
this.MINER_TIMEOUT = 30000;       // 5s → 30s，必须大于节点心跳间隔(15s)
this.STALE_REMOVAL_TIMEOUT = 300000; // 30s → 5min，避免矿工被过早移除
```

**验证**: 矿工显示online ✅

### 问题5: 7900XT推理超时——请求到达节点但矿工未注册

**发现过程**:
- 7900XT推理请求发送后超时(>20秒)
- TCP连接7900XT:9313成功
- 返回"No online miner available"

**根因**: 7900XT矿工没有向本机节点注册（miner_ready RPC未成功）
- 节点9313收到请求 → 转发到127.0.0.1:9332 → 连接失败 → P2P fallback等待120秒

**解法**: 重启7900XT矿工，确保矿工正确向节点发送miner_ready RPC

**验证**: 重启后7900XT推理成功(6108ms) ✅

### 问题6: IPv6隐私扩展导致地址频繁变化 + Web显示IP与矿工注册IP不一致

**发现过程**:
- 每次查询Web矿工列表，7900XT的IPv6地址都不同
- 请求发到Web显示的新IP → "No online miner available"
- 请求发到旧IP（矿工注册时的IP）→ 推理成功

**根因**: Windows IPv6隐私扩展(RFC 4941)默认启用，临时IPv6地址定期更换
- 节点启动时绑定到一个临时IPv6地址
- 矿工向该地址的节点注册
- 一段时间后，Windows生成新的临时IPv6地址
- Web心跳更新为新IP，但矿工仍在旧IP的节点上
- 新IP的节点没有矿工注册 → "No online miner available"

**解法**: 每次推理前从Web API获取最新矿工IP，不缓存旧IP
- 如果新IP返回"No online miner"，尝试旧IP
- 长期方案：配置IPv6永久地址（非隐私扩展临时地址）

**教训**: **禁止缓存IPv6地址！每次调用前必须从Web API获取最新IP**
**重要**: 7900XT需要更新到新版tkncd.exe（含Gateway修复），并配置IPv6永久地址

## 四、远程推理调用完整流程（已验证通过）

### 方式A: IPv6直连推理（矿工IPv6可达时使用）

适用条件：调用方和矿工在同一IPv6子网，或矿工IPv6地址从调用方可达。

#### 步骤1: 检查矿工在线

```powershell
$r = Invoke-RestMethod -Uri 'http://139.196.28.21/api/miners' -Method Get
# 确认7900XT矿工 status=online, 获取最新IPv6地址
```

#### 步骤2: 创建API Key（通过种子节点RPC）

```powershell
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 tknc_createapikey 100 all 365"
# 返回 api_key + synced_peers（必须>0）
```

#### 步骤3: IPv6远程推理（必须用IPv6地址！）

```powershell
$apiKey = 'tknc_xxx'
$ep = 'http://[2408:8244:bb00:6ad:26b8:3302:861e:3d72]:9313/v1/chat/completions'

```

**注意**: 节点9313只监听IPv6 `[::]:9313`，不监听IPv4 `0.0.0.0:9313`，禁止用127.0.0.1:9313！

### 方式B: P2P中转推理（矿工IPv6不可达时使用，推荐）

适用条件：矿工在NAT后、防火墙阻止入站、不同IPv6子网、或任何无法直连矿工9313端口的情况。

**核心原理**：种子节点与7900XT节点有P2P连接（TCP:9333），推理请求通过P2P消息转发，不需要直连矿工的IPv6地址。

```
调用方 → SSH → 种子节点(139.196.28.21) → P2P网络 → 7900XT节点 → 本地矿工(127.0.0.1:9332) → GPU推理
                ↑                                    ↑
           RPC:9331                           P2P:9333
```

#### 步骤1: 检查矿工在线

```powershell
$r = Invoke-RestMethod -Uri 'http://139.196.28.21/api/miners' -Method Get -TimeoutSec 10
# 确认7900XT矿工 status=online
$online7900 = $r.miners | Where-Object { $_.vram_mb -gt 10000 -and $_.status -eq 'online' }
Write-Host "7900XT Endpoint: $($online7900[0].api_endpoint)"
```

#### 步骤2: 查找7900XT的P2P peer_id

```powershell
# 查询种子节点的P2P连接列表
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 getpeerinfo"
# 返回JSON数组，找到7900XT对应的peer id
# 示例: {"id": 672, "addr": "36.34.254.233:8124", "synced_blocks": 889, ...}
```

**如何确认哪个peer是7900XT**：
- 看addr字段：7900XT的公网IPv4地址
- 看synced_blocks：应该>0（已同步的节点）
- 如果只有一个peer，那就是7900XT

#### 步骤3: 通过p2pinference RPC发送推理请求

```powershell
# 基本格式（不带api_key，无计费）
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 p2pinference 'qwen2.5-0.5b-instruct' '你的问题' <peer_id>"

# 示例：推理2+2=?
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 p2pinference 'qwen2.5-0.5b-instruct' '2+2=?' 672"
```

**p2pinference参数说明**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| model | string | 是 | 模型名称，如 `qwen2.5-0.5b-instruct` |
| prompt | string | 是 | 推理提示文本 |
| peer_id | numeric | 否 | 目标peer ID（省略则自动选第一个peer） |
| api_key | string | 否 | API Key（用于escrow计费，省略则不计费） |

**返回值**：

```json
{
  "content": "2+2 equals 4.",
  "tokens_used": 180,
  "cost": 180,
  "peer_id": 672
}
```

| 字段 | 说明 |
|------|------|
| content | 推理结果文本 |
| tokens_used | 消耗的token数 |
| cost | 费用（TKNC） |
| peer_id | 处理请求的peer ID |

#### 步骤4: 带API Key的P2P推理（escrow计费模式）

```powershell
# 先创建escrow（一次性操作）
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 createescrow <wallet> 100 'qwen2.5-0.5b-instruct'"

# 带api_key推理
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 p2pinference 'qwen2.5-0.5b-instruct' '2+2=?' 672 'tknc_xxx'"
```

**注意**: p2pinference的api_key使用escrow计费机制，与Web创建的API Key（LevelDB存储）是不同的计费体系。

#### P2P推理完整测试脚本

```powershell
$sshKey = "$env:USERPROFILE\.ssh\id_ed25519"
$questions = @(
    @{q='2+2=?'; n='Q1'},
    @{q='What is the capital of China?'; n='Q2'},
    @{q='What is the largest planet in the solar system?'; n='Q3'},
    @{q='What is the chemical formula for water?'; n='Q4'},
    @{q='How many days in a year?'; n='Q5'}
)

# 先获取peer_id
$peers = ssh -o BatchMode=yes -i $sshKey root@139.196.28.21 `
  "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 getpeerinfo" 2>&1
$peerId = ($peers | ConvertFrom-Json)[0].id
Write-Host "7900XT peer_id: $peerId"

foreach ($item in $questions) {
    Write-Host "`n=== $($item.n): $($item.q) ==="
    $sw = [System.Diagnostics.Stopwatch]::StartNew()
    $result = ssh -o BatchMode=yes -i $sshKey root@139.196.28.21 `
      "cd /app/seed && ./tknc-cli -rpcuser=tkncadmin -rpcpassword=tkncpass123 -rpcport=9331 p2pinference 'qwen2.5-0.5b-instruct' '$($item.q)' $peerId" 2>&1
    $sw.Stop()
    try {
        $json = $result | ConvertFrom-Json
        Write-Host "Answer: $($json.content)"
        Write-Host "Tokens: $($json.tokens_used) | Peer: $($json.peer_id) | Total: $($sw.ElapsedMilliseconds)ms"
    } catch {
        Write-Host "Result: $result"
        Write-Host "Total: $($sw.ElapsedMilliseconds)ms"
    }
    Start-Sleep -Seconds 1
}
```

### 问题8: 前端POST请求缺少CSRF token导致支付/创建Key失败

**发现过程**:
- 点击"确认支付并获取API Key"→ 页面显示"获取支付签名失败: CSRF token validation failed"
- 检查server.js CSRF中间件(L296-324): POST/PUT/DELETE请求需要`x-csrf-token`头
- 检查前端index.html: 所有POST请求只传了`x-session-token`，没有传`x-csrf-token`

**根因**: 前端JS代码在发送POST请求时，没有在请求头中传递`x-csrf-token`。登录时服务器返回了`csrf_token`并存储在`currentUser.csrf_token`中，但后续请求没有使用。

**修复**: `index.html`中7处POST/DELETE请求添加`x-csrf-token`头:
1. `/api/payment/nonce` (3处: 评论、邀请、API Key)
2. `/api/create_key` (1处)
3. `/api/comments` POST (1处)
4. `/api/comments/{id}` DELETE (1处)
5. `/api/miners/set-price` POST (1处)
6. `/api/miners/set-public-ip` POST (1处)
7. `/api/comments/invite` POST (1处)

**修改示例**:
```javascript
// 修改前
headers: { 'Content-Type': 'application/json', 'x-session-token': currentUser.session_token }

// 修改后
headers: { 'Content-Type': 'application/json', 'x-session-token': currentUser.session_token, 'x-csrf-token': currentUser.csrf_token }
```

**验证**: 点击"确认支付并获取API Key"→ 支付签名对话框正常弹出 ✅

### 问题9: I18N.html MIME类型错误导致页面功能异常

**发现过程**:
- 页面刷新后矿工列表显示"加载矿工中..."，无法加载
- 浏览器控制台报错: `Refused to execute script from 'I18N.html' because its MIME type ('text/html') is not executable`
- `I18N_DICT is not defined` → JS翻译函数无法工作

**根因**: `index.html`中`<script src="I18N.html">`引用了`.html`扩展名的JS文件。Express的`express.static`中间件根据扩展名设置MIME类型，`.html`被设置为`text/html`，浏览器拒绝执行非JS MIME类型的脚本。

**修复**:
1. 在远程服务器上: `cp /app/web/public/I18N.html /app/web/public/I18N.js`
2. 在index.html中: `<script src="I18N.html">` → `<script src="I18N.js">`

**验证**: 页面刷新后矿工列表正常加载，中文翻译正常显示 ✅

### 问题10: DEV_MODE下余额不足检查阻止API Key创建

**发现过程**:
- 支付签名验证通过后，页面显示"创建失败: Insufficient balance. Current: 0 TKNC, Required: 100 TKNC"
